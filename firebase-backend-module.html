SiteWalk — Firebase Persistent Backend

Why Firebase

Every module so far (punch list, RFIs, daily logs, submittals, safety log, GPS clock events, trade directory) stores data in localStorage, which only lives on one device/browser. Firebase Firestore replaces that with real cloud storage — no server to rent or maintain, works from the same client-side JS you already have, and has a free tier that comfortably covers a pilot with 2-3 developers.

Setup Steps (for Grok / whoever wires this in)

  1. Go to console.firebase.google.com, create a project (free "Spark" plan).
  2. Enable Firestore Database (start in test mode for the pilot, lock down security rules before going live with real customers).
  3. In Project Settings, register a "Web App" to get a config object (apiKey, projectId, etc.).
  4. Add the Firebase SDK script tags and config below to every SiteWalk HTML file.
  5. Replace every module's load() / save() localStorage calls with the Firestore equivalents below.

Drop-in Replacement for load()/save()

  
This keeps the exact same function names used across all the modules built so far, so Grok can

What changes in each module

  
Because load() becomes async (Firestore reads happen over the network), every place that does:

  
let rfis = load('swRFIs');

  
needs to become:

  
let rfis = [];
loadCollection('swRFIs').then(data => { rfis = data; renderRFIs(); });

  
And every save(key, fullArray) call becomes an individual addDoc/updateDoc/deleteDoc
  call per item (see helper functions below) — Firestore works per-document, not as one big array dump like localStorage.






  
Real-time sync (recommended)

  
Instead of a one-time loadCollection(), using onSnapshot() means every device sees
  updates live — e.g. a supervisor clears a punch item and it disappears from the sub's phone instantly. Worth
  having Grok wire this in from the start rather than retrofitting later.
